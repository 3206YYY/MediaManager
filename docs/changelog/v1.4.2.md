# v1.4.2 — 列表提速 200 倍，而且这次有据可查

## 先说这一版为什么存在

发完 v1.4.1 之后被问了一个问题：改了这么多代码，性能真的有提升吗？跑分是怎么测的？

查完发现**答不上来**。README 上写着「实测十万张图滚动丝滑，内存占用硬顶 200MB」，但：

- 仓库里没有任何基准脚本、没有任何测量记录；
- 那句话里的「200MB」其实是**缩略图缓存的字节预算**，被误写成了进程内存上限；
- 本机日志显示只有 20 张缩略图时工作集就到 215MB，历史峰值 364MB。

所以这一版做的事是：**先把测量做出来，再让测量结果决定改什么**。

---

## 一、列表查询快了 20~200 倍

新增 `build/bench_db.py`：复制一份真实库结构，灌入 10 万条合成元数据，跑仓库里
**真实在用的那几条 SQL**，输出 p50 / p95。10 万条、同一台机器、同一份数据生成器：

| 场景 | v1.4.1 | v1.4.2 | 提升 |
|---|---:|---:|---:|
| 主列表首页 100 条 | 79.3 ms | **0.43 ms** | 186× |
| 翻到第 5 万条 | 2371.8 ms | **12.2 ms** | 195× |
| 按名称排序首页 | 72.3 ms | **0.36 ms** | 201× |
| 总数统计 | 64.5 ms | **3.1 ms** | 21× |
| 按文件夹分组计数 | 1050.1 ms | **7.1 ms** | 148× |
| FTS 关键词搜索 | 0.013 ms | 0.015 ms | 持平 |
| trigram 子串搜索 | 0.134 ms | 0.137 ms | 持平 |

**根因**：查询条件里 `IsPrivate = 0` 是布尔列，选择性接近 100%，但 SQLite 的优化器
偏偏选中了 `IX_Media_Private`。一旦用它过滤，就再也利用不上 `DateAddedUtc` 的有序性，
只能对全表做临时 B-TREE 排序 —— 翻到第 5 万条要 2.4 秒，就是这么来的。

**解法**：加 4 个复合索引（`IX_Media_Feed` / `IX_Media_NameFeed` / `IX_Media_Active` /
`IX_Media_RootActive`），让排序直接走索引顺序。

**代价**（也说清楚）：写入慢约 34~50%（10 万条多花 20~50 秒，属于一次性扫描成本），
库体积约 +14%（10 万条约 67 MB → 77 MB）。用一次性成本换每次翻页的体感。

> ⚠ 老库升级后**第一次启动会多花 1~2 秒**建这四个索引，之后就没了。

## 二、修掉一个「升级即崩」的隐患

加索引时差点犯一个错：`IsPrivate` 是 v1.3.4 才给老库 `ALTER TABLE` 补上的列，
如果把索引写在建表语句旁边，**v1.3.x 用户升级时会直接 `no such column: IsPrivate`，
初始化整个失败，程序起不来**。

这个坑在代码注释里前人已经记过一次。现在补了 `SchemaMigrationTests`：造一个
v1.3.3 结构的旧库，跑初始化，断言不抛异常、列补上、索引建出来、查询计划真的用上新索引。

而且验证了这个测试**确实会红**：把索引挪回错误位置后 3 个用例全失败，报的正是
`no such column: IsPrivate`。

## 三、把「验证通过」变成可复现

以前每一版都写「实机 20/20 通过」，但那些脚本被 `.gitignore` 排除了 —— 别人 clone
下来根本跑不了，等于只有出图那台机器上的口头承诺。

现在 `build/verify/` 进了仓库：

| 脚本 | 验什么 |
|---|---|
| `verify_external_open.py` | 非核心类型外放、图片仍走内置查看器 |
| `verify_vault_password.py` | 密码全生命周期（设/解锁/输错重试/改/取消/库无残留） |
| `verify_diary_calendar.py` | 日历弹窗深色渲染、点日期写回、年视图 12 格、点月跳转 |
| `verify_light_theme.py` | 浅色主题没被深色改动弄坏 |

配套 `build/verify/README.md` 写了前置条件、判据（为什么用平均亮度）、以及
**已知局限**（只覆盖写进脚本的路径、没有性能断言、换 DPI 可能失效、不属于 CI）。

顺手收紧了一条弱判据：原来「打开 txt 交给系统」只要**出现任意新进程**就判 PASS，
实测抓到过 `bash.exe` 顶包（那是跑脚本的宿主进程）。现在排除宿主/系统噪声进程，
并要求出现已知的文档程序名，否则判红并打印实际进程名 —— 宁可红，不要假绿。

## 四、把「不设密码」的边界写清楚

密码功能保留，但说明文字改成实话：

> 说实话：这是一道「防顺手」的门，不是加密保险箱。挡得住别人坐在你电脑前随手点开；
> 挡不住能操作这台电脑文件的人 —— 凭据就存在同一个数据库里，删掉 `Vault.Credential`
> 那一行即失效，文件本身也不加密，就在数据目录的 Vault 文件夹里。
> 真要防取证，请用 VeraCrypt 这类真加密工具。

解锁窗也补了逃生路径：忘了密码去「设置 → 数据目录 → 打开数据目录」，Vault 文件夹能直接拷。

## 五、删掉一句没有依据的话

README 里「实测十万张图滚动丝滑，内存占用硬顶 200MB」已删除，换成可复跑的数字，
并注明**只测 SQL 层、不含界面渲染和内存峰值**。

## 六、类型分流收敛到一处

打开策略本来有 4 份平行实现，其中 1 份是永远走不到的死代码（`VaultWindow` 里
`case Audio/Text/Archive`，前面早被 `MediaOpenStrategy` 拦走了）。现在：

- 缩略图任务改用 `MediaOpenStrategy.UseExternalApp()` 判断，不再另抄一份枚举；
- 死代码删除；
- 「扩展格式」和「外放类型」是两个概念，不强行合并实现，但加了一条交叉测试钉住
  当下的一致性 —— 将来分叉时测试会红，逼人确认那是不是有意为之。
